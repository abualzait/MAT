# المواصفات التصميمية: قسم إدارة الشكاوى الأمنية الذكية (MAT Police Complaints Intake & Approval Workflow)

**تاريخ التصميم:** 2026-11-10  
**المشروع:** MAT (Modular Assistant Toolkit) — حقيبة الأدوات المساعدة / محافظة العاصمة  
**الإصدار المستهدف:** `v1.46.0` (ترقية من `v1.45.20`)  
**المرجع الورقي المعتمد:** [`complaint_form_editable.docx`](../../complaint_form_editable.docx)

---

## 1. نطاق القسم وأهدافه (Scope & Objectives)

إضافة قسم متكامل لإدارة الشكاوى الخفيفة التي تتطلب تدخل أو وجود الشرطة (المقدمة من **مواطنين** أو **مؤسسات تجارية** أو **مؤسسات حكومية** ضد **مواطن** أو **منشأة**) داخل حقيبة أدوات **MAT**، بدءاً من مسح نموذج الشكوى المعبأ بخط اليد عبر السكانر، مروراً باستخراج البيانات وتحليلها عبر نموذج ذكاء اصطناعي متعدد المزودين (LLM Vision)، فمراجعة الضابط واتخاذ الإجراء وكتابة الملاحظات، ثم تنسيب رئيس قسم الشكاوى، وانتهاءً بقرار الحاكم الإداري (المتصرف) إلكترونياً، مع تكامل تلقائي كامل مع باقي أدوات الحقيبة (دليل المراكز الأمنية، نظام المواعيد والاتصالات، أداة حجز الملفات، الإشعارات وغرفة الاجتماعات).

---

## 2. البديل المعماري المعتمد (Chosen Architecture)

اعتماد **الوحدات المعزولة المتكاملة مع نواة MAT (`Modular Python + JS`)**:
- **الخادم الخلفي (Zero-Dependency Python Standard Library):**
  - إنشاء وحدة [`mat_llm_engine.py`](../../mat_llm_engine.py): موصل LLM Vision متعدد المزودين (`Gemini`، `OpenAI / Compatible`، `Ollama` محلي) باستخدام `urllib.request` و`json` و`base64` فقط دون تبعيات خارجية إضافية، مع تعقيم الاستجابات وإلزامها بمخطط JSON محدد.
  - إنشاء وحدة [`mat_complaints_service.py`](../../mat_complaints_service.py): منطق دورة حياة الشكوى، تخزين وتحقق الملفات الممسوحة عبر فحص `Magic Bytes` بمكتبات بايثون القياسية فقط، مطابقة عنوان المشتكى عليه مع [`data/amman_areas.json`](../../data/amman_areas.json) لإيجاد أقرب مركز أمني، التكامل التلقائي مع `mat_simple_appointments` و`mat_reserved_files` والإشعارات، حساب عدّاد الـ 90 يوماً، وتوليد نموذج Word الرسمي المعبأ (`.docx`) بالاعتماد على قالب [`complaint_form_editable.docx`](../../complaint_form_editable.docx) عبر مكتبات بايثون القياسية (`zipfile` و`xml.etree.ElementTree`) للحفاظ على التوافق التام مع حاوية `Dockerfile` الخالية من التبعيات الخارجية.
  - ربط المسارات الجديدة داخل [`server.py`](../../server.py) ضمن النطاق القياسي `/api/v1/mat/police-complaints/*` و`/api/v1/mat/llm-settings`، وتحديث `init_db()` (مع تسمية الفهارس ببادئة `idx_mat_*`) و`backup_db_to_json()` و`restore_db_from_json()`.
- **الواجهة الأمامية (Vanilla HTML/CSS/JS):**
  - إضافة التبويب والقوالب والنوافذ المنبثقة داخل [`complaints/app.html`](../../complaints/app.html) (وفق نظام التصميم الحالي `design-system.css`).
  - عزل منطق الواجهة الخاص بالقسم في ملف مستقل [`complaints/js/police_complaints.js`](../../complaints/js/police_complaints.js) مع تسجيل التبويب والصلاحية الجديدة `police_complaints` في [`complaints/js/app.js`](../../complaints/js/app.js).
  - إضافة حساب ودور **الحاكم الإداري (`governor`)** في بوابة الدخول [`complaints/login.html`](../../complaints/login.html).

## 3. الأدوار وصلاحيات الوصول (Roles & RBAC)

| الدور (`role`) | المسمى العربي | الصلاحيات والمسؤوليات في قسم الشكاوى |
| :--- | :--- | :--- |
| **`officer`** | موظف / ضابط شكاوى | مسح الشكوى ضوئياً، تشغيل الاستخراج والتحليل الذكي، تدقيق/تعديل البيانات المستخرجة، إرسال الشكوى لرئيس القسم، وكذلك **النظر في الشكوى واتخاذ الإجراء المناسب عليها وكتابة الملاحظات** (سواء عند التقييم المبدئي أو أثناء المتابعة وتنفيذ القرار المعتمد). |
| **`admin`** | رئيس قسم الشكاوى (`orwa` أو من بصلاحية مشرف) | جميع صلاحيات الإدخال والمراجعة، إضافة إلى شاشة **مراجعة رئيس القسم**: تصفح الورقة الممسوحة والبيانات والتوصية الذكية وملاحظات الضابط، كتابة **«مشروحات القسم»**، اختيار **«الإجراء المنسب»** (مع المركز الأمني الأقرب)، رفعها للحاكم الإداري، وإدارة إعدادات مزودي LLM. |
| **`governor`** | الحاكم الإداري (عطوفة المتصرف) | حساب إلكتروني مستقل مخصص للاعتماد: استعراض الشكاوى المرفوعة من رئيس القسم مع كامل المرفقات والتحليل وملاحظات الضابط ومشروحات القسم، ثم اتخاذ القرار الإلكتروني الحصري: **موافقة**، **رفض**، أو **تغيير الإجراء المنسب** مع تدوين قراره وملاحظاته. |
| **`caller`** | ضابط اتصال | الاطلاع على مهام الاتصال الهاتفي الناتجة تلقائياً في نظام المواعيد عند اعتماد إجراء `اتصال هاتفي`. |

## 4. مخطط قاعدة البيانات (Database Schema Design)

جميع الجداول والترحيلات تتبع معيار `mat_` وتعمل عبر `init_db()` دون فقدان أي بيانات قائمة:

### 4.1 تحديث `mat_officers`
- توسيع قيد الدور `CHECK(role IN ('admin', 'officer', 'caller', 'governor'))` (عبر ترحيل آمن للجدول عند الحاجة إذا كان القيد القديم لا يتضمن `governor`).
- إضافة مستخدم افتراضي جديد إذا لم يكن موجوداً: `('عطوفة المتصرف', 'governor', '12345', 'governor', 'dashboard,police_complaints,finder,chat')`.
- منح المستخدمين الفعّالين صلاحية `police_complaints` في `accessible_tools` (أو تفعيلها حسب جدول الصلاحيات المتقدمة).

### 4.2 توسيع `mat_complaints`
إضافة الأعمدة التالية إلى الجدول القائم `mat_complaints` عبر `ALTER TABLE` الآمن في `init_db()`:
- `paper_date TEXT` — تاريخ الشكوى المثبت في النموذج الورقي.
- `complainant_category TEXT DEFAULT 'مواطن'` — (`مواطن` / `مؤسسة تجارية` / `مؤسسة حكومية`).
- `respondent_category TEXT DEFAULT 'مواطن'` — (`مواطن` / `منشأة`).
- `summary TEXT` — موجز الشكوى المستخرج من خط اليد.
- `has_signature INTEGER DEFAULT 0` و`no_pending_lawsuit_declared INTEGER DEFAULT 0` — إقرار عدم وجود قضايا منظورة أمام القضاء وتوقيع المشتكي.
- `workflow_stage TEXT DEFAULT 'draft_scan'` — مرحلة سير العمل:
  - `draft_scan` (مسودة مسح ضوئي)
  - `officer_reviewed` (تمت مراجعة الضابط وكتابة ملاحظاته)
  - `pending_section_head` (بانتظار مراجعة وتنسيب رئيس القسم)
  - `pending_governor` (بانتظار قرار الحاكم الإداري)
  - `governor_approved` (معتمدة من الحاكم الإداري)
  - `governor_modified` (معتمدة مع تغيير الإجراء المنسب)
  - `governor_rejected` (مرفوضة من الحاكم الإداري)
  - `in_execution` (قيد التنفيذ والمتابعة من الضابط)
  - `completed` (منجزة / مغلقة)
  - `stopped_90_days` (كف طلب لعدم المتابعة 90 يوماً)
- `is_minor_police_complaint INTEGER DEFAULT 1` — تقييم ملاءمة الشكوى (مشكلة خفيفة تتطلب تدخل/وجود شرطة).
- `ai_provider TEXT`, `ai_model TEXT`, `ai_extracted_json TEXT`, `ai_analysis TEXT`, `ai_solution_recommendation TEXT`, `ai_recommended_action TEXT`, `ai_confidence REAL`.
- `officer_action TEXT`, `officer_notes TEXT`, `officer_reviewed_by_id INTEGER`, `officer_reviewed_at TEXT` — **الإجراء المتخذ والملاحظات المكتوبة من الضابط عند النظر بالشكوى**.
- `section_head_notes TEXT` (مشروحات القسم), `section_recommended_action TEXT` (الإجراء المنسب), `section_head_id INTEGER`, `section_head_at TEXT`.
- `governor_decision TEXT` (`موافقة` / `رفض` / `تغيير_الإجراء`), `governor_final_action TEXT`, `governor_notes TEXT`, `governor_id INTEGER`, `governor_decided_at TEXT`.
- `nearest_station TEXT`, `police_directorate TEXT`, `liwa_name TEXT`, `station_lat REAL`, `station_lon REAL`.
- `linked_appointment_id INTEGER`, `linked_file_number TEXT`.
- `last_followup_at TEXT DEFAULT (datetime('now', 'localtime'))` — أساس احتساب قاعدة الـ 90 يوماً.

### 4.3 توسيع `mat_parties`
- إضافة عمود `party_category TEXT DEFAULT 'مواطن'` لتمييز المواطن عن المؤسسة التجارية / الحكومية / المنشأة.

### 4.4 جداول جديدة
1. **`mat_complaint_scans`**:
   - `id`, `complaint_id` (FK -> `mat_complaints.id` ON DELETE CASCADE), `stored_filename` (UUID آمن), `original_filename` (منظّف للعرض فقط), `mime_type`, `file_size`, `page_order`, `ocr_raw_text`, `uploaded_by_id`, `created_at`.
2. **`mat_complaint_workflow_log`**:
   - `id`, `complaint_id` (FK), `actor_id` (FK), `actor_role`, `stage_from`, `stage_to`, `action_taken`, `notes`, `created_at`.
3. **`mat_llm_settings`**:
   - `id` (صف مفرد `id=1` للإعداد النشط)، `provider` (`gemini` / `openai` / `ollama`), `model_name`, `api_base_url`, `api_key`, `is_enabled`, `updated_by_id`, `updated_at`.
   - مع دعم متغيرات `.env` الافتراضية (`MAT_LLM_PROVIDER`, `MAT_GEMINI_API_KEY`, `MAT_OPENAI_API_KEY`, `MAT_OLLAMA_URL`, `MAT_LLM_MODEL`) بحيث تأخذ القيم المخزنة في الإعدادات الأولوية إذا تم ضبطها من المشرف.

*(تُضاف الجداول الجديدة تلقائياً إلى `backup_db_to_json` و`restore_db_from_json` باستثناء تضمين مفتاح API في أي مخرج غير مشفر أو واجهة، وتخزن مرفقات السكانر في `data/complaint_scans/`).*

## 5. سير العمل التفصيلي (End-to-End Business Workflow)

### المرحلة 1: المسح الضوئي والاستخراج والتحليل الذكي (Employee / Intake)
1. يضغط الموظف على تبويب **«⚖️ الشكاوى الأمنية الذكية»** ← **«📷 مسح شكوى جديدة»**.
2. يرفع صورة/ملف السكانر (JPG, PNG, WEBP, PDF) عبر السحب والإفلات أو اختيار الملف أو الكاميرا/اللصق.
3. يتم حفظ الممسوحة في الخادم وإرسالها إلى محرك `mat_llm_engine.py` عبر المزود المفعل (Gemini / OpenAI / Ollama):
   - يستخدم المحرك موجهاً (System Prompt) مخصصاً لبنية [`complaint_form_editable.docx`](../../complaint_form_editable.docx) لقراءة الخط اليدوي العربي واستخراج:
     - التاريخ، بيانات المشتكين (1 فأكثر) مع تصنيف كل طرف، بيانات المشتكى عليهم (1 فأكثر) مع تصنيف كل طرف وعنوانه، موضوع الشكوى، موجز الشكوى، وحالة التوقيع والإقرار.
   - يحلل النموذج المضمون لتحديد:
     - هل تتطلب الشكوى وجود شرطة (مشكلة خفيفة تقع ضمن الاختصاص الإداري/الأمني) أم لا.
     - التوصية بالحل المقترح والإجراء الأنسب:
       - `توديع عن طريق مركز أمني` (مع إبراز عنوان المشتكى عليه المقترح للربط)
       - `اتصال هاتفي`
       - `توديع مغفور`
       - `حفظ / توجيه للقضاء المختص`
4. يعرض النظام **معاينة مقسمة (Split View)**: صورة الورقة الممسوحة يميناً، والبيانات المستخرجة + بطاقة التحليل والتوصية الذكية يساراً، مع مطابقة فورية لعنوان المشتكى عليه مع [`data/amman_areas.json`](../../data/amman_areas.json) لاقتراح **المركز الأمني الأقرب والمديرية واللواء** تلقائياً.
5. يراجع الموظف الحقول ويصحح أي حرف إذا لزم، ثم يحفظ ويرسل الشكوى (`إرسال لرئيس القسم` أو `إسناد لضابط للمراجعة`).

### المرحلة 2: نظر الضابط في الشكوى واتخاذ الإجراء وكتابة الملاحظات (Officer Review & Action)
- عند فتح الشكوى من قبل **الضابط (`officer` أو `admin`)** في أي من مرحلتي النظر المبدئي أو المتابعة التنفيذية:
  - تظهر بطاقة **«👮 قرار وملاحظات الضابط»** متضمنة:
    - استعراض الممسوحة الضوئية + البيانات المستخرجة + توصية الذكاء الاصطناعي + المركز الأمني الأقرب.
    - حقل اختيار **الإجراء المناسب المتخذ/المقترح** (`توديع عن طريق مركز أمني`، `اتصال هاتفي`، `توديع مغفور`، `مواجهة / تسوية ودية`، `إعادة استكمال نواقص`، `إغلاق بعد التنفيذ`).
    - حقل **«ملاحظات الضابط»** (إلزامي عند اتخاذ الإجراء).
    - عند الحفظ، تُوثق ملاحظات الضابط وإجراؤه في `mat_complaints` وفي السجل الزمني `mat_complaint_workflow_log` مع تحديث المرحلة بوضوح:
      - في مرحلة التقييم المبدئي (`draft_scan` / `officer_reviewed` / `governor_rejected`): تنتقل إلى `officer_reviewed` أو تُرفع مباشرة إلى `pending_section_head` حسب خيار الضابط.
      - في مرحلة ما بعد قرار الحاكم الإداري (`governor_approved` / `governor_modified` / `in_execution`): تنتقل إلى `in_execution` (قيد التنفيذ) أو `completed` (منجزة / مغلقة) حسب نتيجة التنفيذ المسجلة.

### المرحلة 3: مراجعة وتنسيب رئيس قسم الشكاوى (Section Head Review)
- يفتح رئيس القسم قائمة **«بانتظار تنسيب رئيس القسم»** ويرى:
  - الوثيقة الممسوحة + البيانات + توصية الذكاء الاصطناعي + ملاحظات وإجراء الضابط.
  - المركز الأمني الأقرب المحتسب آلياً لعنوان المشتكى عليه مع زر لتأكيده أو تعديله من دليل المراكز.
- يكتب **«مشروحات القسم»** ويحدد **«الإجراء المنسب»** (`توديع عن طريق مركز أمني`، `اتصال هاتفي`، `توديع مغفور`، `حفظ / عدم اختصاص`) ثم يضغط **«📤 رفع للحاكم الإداري للاعتماد»**.
- يصل إشعار فوري للحاكم الإداري.

### المرحلة 4: قرار الحاكم الإداري الإلكتروني (Governor Decision)
- يسجل **الحاكم الإداري (`governor`)** دخوله بحسابه الخاص، فتظهر له لوحة الاعتمادات المعلقة:
  - يطّلع على ملخص الشكوى، صورة النموذج اليدوي، توصية الذكاء الاصطناعي، ملاحظات الضابط، ومشروحات رئيس القسم والإجراء المنسب.
  - يتخذ أحد القرارات الثلاثة حصراً:
    1. **✅ موافقة على الإجراء المنسب**
    2. **✏️ تغيير الإجراء المنسب** (يختار الإجراء الجديد والمركز الأمني إن وجد + سبب التعديل)
    3. **❌ رفض التنسيب** (مع كتابة سبب الرفض، وتتحول الشكوى لمرحلة `مرفوض من الحاكم الإداري` أو تُعاد للقسم لإعادة التوجيه).

### المرحلة 5: التكامل التلقائي مع أدوات MAT (Automated Toolkit Integrations)
بمجرد صدور قرار **الموافقة** أو **تغيير الإجراء المنسب** من الحاكم الإداري:
1. **إذا كان الإجراء `توديع عن طريق مركز أمني` أو `توديع مغفور`:**
   - تثبيت المركز الأمني الأقرب لعنوان المشتكى عليه والمديرية واللواء (أو اختياره يدوياً إذا لم يُطابق آلياً).
   - حجز/ربط رقم ملف الشكوى تلقائياً في أداة حجز الملفات (`mat_reserved_files`) باسم الضابط المكلف أو رئيس القسم مع تسجيل قيد في `mat_file_custody_log` (إذا لم يكن الرقم محجوزاً مسبقاً).
   - تفعيل زر **«📄 طباعة/تصدير نموذج التوديع الرسمي (.docx)»** المبني على [`complaint_form_editable.docx`](../../complaint_form_editable.docx) مضافاً إليه مشروحات القسم وقرار الحاكم الإداري والمركز الأمني المعني.
2. **إذا كان الإجراء `اتصال هاتفي`:**
   - إنشاء سجل موعد/اتصال تلقائي في **`mat_simple_appointments`** باسم المشتكى عليه/المشتكي ورقم هاتفه ورقم الشكوى والمركز الأمني وملاحظات القسم والحاكم الإداري، ليظهر مباشرة لدى ضابط الاتصال (`caller`) في جدول المواعيد.
3. **تنبيهات غرفة الاجتماعات وFCM:**
   - إرسال إشعارات فورية في نظام الإشعارات وFCM عند الإرسال لرئيس القسم، الرفع للحاكم الإداري، وعند صدور قرار الحاكم الإداري.
4. **عدّاد الـ 90 يوماً (قاعدة كف الطلب):**
   - احتساب الأيام المنقضية منذ `last_followup_at`، وإظهار شارة تحذيرية عند الاقتراب من 90 يوماً (مثلاً ≥ 75 يوماً) وشارة استحقاق **«⚠️ تجاوز 90 يوماً — مستحق لكف الطلب»** مع زر تحديث مراجعة المشتكي أو تفعيل كف الطلب.

## 6. مسارات الـ API الجديدة (API Contracts)

جميع المسارات تتطلب جلسة مصادقة سارية وتحقق `CSRF` لطلبات الكتابة (`POST`/`PUT`/`DELETE`):
- `GET /api/v1/mat/police-complaints` — قائمة الشكاوى مع فلاتر المرحلة، البحث، وتجاوز 90 يوماً وإحصائيات لوحة القسم.
- `GET /api/v1/mat/police-complaints/<id>` — تفاصيل الشكوى الكاملة، الأطراف، المرفقات الممسوحة، السجل الزمني، الموعد المرتبط، والملف المحجوز.
- `POST /api/v1/mat/police-complaints/scan-extract` — رفع ملف السكانر (Multipart أو Base64 JSON آمن) وتشغيل استخراج وتحليل LLM وإرجاع الحقول المقترحة + أقرب مركز أمني.
- `POST /api/v1/mat/police-complaints` — حفظ/إنشاء الشكوى (مسودة أو إرسال لرئيس القسم) مع التحقق من الأطراف والمرفق.
- `PUT /api/v1/mat/police-complaints/<id>` — تحديث بيانات الشكوى أو تسجيل متابعة الشاكي (إعادة ضبط عداد 90 يوماً) أو تفعيل كف الطلب.
- `POST /api/v1/mat/police-complaints/<id>/officer-action` — نظر الضابط بالشكوى، تسجيل الإجراء المناسب وملاحظات الضابط، وتحديث المرحلة/الحالة (`officer`, `admin`).
- `POST /api/v1/mat/police-complaints/<id>/section-recommend` — كتابة مشروحات القسم وتنسيب الإجراء ورفعها للحاكم الإداري (`admin`).
- `POST /api/v1/mat/police-complaints/<id>/governor-decision` — قرار الحاكم الإداري (`موافقة` / `رفض` / `تغيير الإجراء المنسب`) وتنفيذ التكامل التلقائي (`governor` فقط).
- `GET /api/v1/mat/police-complaints/scans/<scan_id>` — عرض صورة/ملف السكانر للمصرح لهم فقط مع ترويسة `X-Content-Type-Options: nosniff`.
- `GET /api/v1/mat/police-complaints/<id>/export-docx` — توليد وتنزيل نموذج `.docx` الرسمي المعبأ بالبيانات ومشروحات القسم وقرار المتصرف.
- `GET /api/v1/mat/police-complaints/match-station?address=...` — مطابقة العنوان مع `amman_areas.json` وإرجاع أقرب مركز أمني والمديرية واللواء.
- `GET / PUT /api/v1/mat/llm-settings` — قراءة (مع إخفاء المفتاح) وتحديث إعدادات مزود LLM (`admin` فقط) + `POST /api/v1/mat/llm-settings/test` لاختبار الاتصال.

## 7. الضوابط الأمنية والاختبار (Security & Verification Plan)

- **منع حقن SQL:** استخدام استعلامات SQL المعلمة (`?`) حصراً في جميع الاستعلامات.
- **منع XSS:** عدم استخدام `innerHTML` مع أي نص مستخرج من السكانر أو LLM أو مدخلات المستخدم؛ استخدام `document.createElement` و`textContent` ودالة `escapeHtml` المحكمة.
- **أمن رفع الملفات:** فحص الامتداد والمحتوى الفعلي (`Magic Bytes`) للصور (`JPEG/PNG/WEBP`) و`PDF`، حد أقصى `10MB`، إعادة التسمية إلى `UUID`، التخزين خارج الجذر العام للويب في `data/complaint_scans/`، ومنع استدعاء المسارات النسبية (`../`).
- **حماية المفاتيح:** عدم إرجاع مفاتيح API من الخادم إلى الواجهة، وعدم تسجيلها في السجلات (`logs`) أو `data_backup.json`.
- **حماية الجلسات:** ضبط خاصية `HttpOnly` على كوكي الجلسة `session` مع بقاء `SameSite=Lax` والتحقق من `CSRF` في جميع طلبات التعديل.
- **خطة التحقق:**
  1. اختبارات وحدة (`unittest` / `pytest`) لمحرك مطابقة المراكز الأمنية، وقواعد سير العمل وصلاحيات الأدوار (`officer` vs `admin` vs `governor`)، وحماية رفع الملفات، وعدّاد 90 يوماً، وتوليد ملف `.docx`.
  2. اختبارات تكامل API على خادم محلي يستمع على `127.0.0.1` تغطي الدورة الكاملة: مسح ← تحليل ← مراجعة الضابط ← تنسيب رئيس القسم ← قرار الحاكم الإداري (موافقة / رفض / تغيير) ← التحقق من إنشاء الموعد التلقائي وحجز الملف.
  3. فحص الواجهة في المتصفح ومراجعة مخرجات التصدير وتوافق الشاشات.
